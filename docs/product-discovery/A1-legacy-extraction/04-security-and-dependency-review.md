## 2. Cross-cutting red flags

- **Auth:** legacy passes RLS-aware clients and derives `userId` from `requireUser()`; greenfield must keep session-derived identity (`client.auth.getUser()`), no user-ID args, middleware never bootstraps (G1 invariant).
- **RLS:** legacy `is_org_member/admin/owner`, `is_finder_*_captain`, `has_tool_access`, `can_manage_finder_avatar/evidence` are reference shapes only. Fresh policies required per new table; no file copy.
- **Service-role:** legacy stores, webhook fulfillment, admin reads, and cron writers use admin client. Greenfield: isolate to `src/server/` only; never import from client components (enforced by `routes.test.ts` pattern).
- **Secrets:** all provider/OAuth/webhook keys must be re-provisioned; `CRON_SECRET`, `YOUTUBE_WEBSUB_VERIFY_TOKEN`, `BILLING_LIVE_TEST_*` currency unverified — confirm vs live project before any reuse or deletion.
- **Cron:** greenfield `vercel.json` has no crons by design. Any ingest/scan/retention cron needs product + architecture approval + ledger from day one.
- **Billing coupling:** entitlement checks (`has_tool_access`, `is_all_access`, `consume_*`) are inseparable from legacy org model. Do not port checks without the new org/entitlement design.
- **PII:** masked views omit `user_id/email/game_user_id/evidence/external_link`; `escapeCsvCell` guards formula injection; audit `safeAuditProjection` redacts secrets. Preserve all three in reimplementations.
